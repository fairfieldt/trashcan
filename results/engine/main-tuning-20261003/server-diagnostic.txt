Diagnostic-only resident server profiling

Files:
- server-diagnostic.patch: unified diff against engine/src/server.rs identified by server-diagnostic-base.json.
- server-diagnostic.py: standard-library HTTP replay client (Python 3 urllib.request).
- server-diagnostic-base.json: unpatched and patched source SHA-256.

Production engine files have not been modified by preparing these files. The patch was compiled
with Clippy in a temporary source mirror, now removed; that only verifies CPU compilation on this Mac, where
glslc is unavailable. The client was exercised with synthetic local JSON and SSE responses.
No GPU command or remote command was run for this preparation.

Wait until the existing queued GPU job has ended. Do not modify/build the shared checkout while
another benchmark is building it. Run the following from ~/trashcan on incite. This preserves
uncommitted source; do not use git checkout, git reset, or git stash to remove the diagnostic patch.

    set -euo pipefail
    diag_root=results/engine/main-tuning-20261003
    diag_patch="$diag_root/server-diagnostic.patch"
    diag_backup=$(mktemp)
    cp engine/src/server.rs "$diag_backup"
    sha256sum engine/src/server.rs
    # Compare the SHA above with server-diagnostic-base.json before proceeding.
    git apply --check "$diag_patch"
    git apply "$diag_patch"
    restore_diagnostic_source() {
        git apply --reverse --check "$diag_patch" && git apply --reverse "$diag_patch"
    }
    trap restore_diagnostic_source EXIT
    cargo build --release --target-dir target/server-diagnostic --manifest-path engine/Cargo.toml
    sha256sum target/server-diagnostic/release/trashcan > "$diag_root/server-diagnostic-binary.sha256"
    sha256sum engine/src/server.rs > "$diag_root/server-diagnostic-source.sha256"
    restore_diagnostic_source
    trap - EXIT
    cmp engine/src/server.rs "$diag_backup"
    rm "$diag_backup"

The production target/release/trashcan remains unchanged. The diagnostic binary stays separately
at target/server-diagnostic/release/trashcan after source restoration. If reverse-check fails,
stop and inspect the intervening source change; do not overwrite it with the backup blindly.

Run each diagnostic server sequentially, with a fresh output directory for each process. Set the
environment variable after latency-run.py (sudo may otherwise strip it). A cold ordinary example:

    diag_run="$PWD/results/engine/main-tuning-20261003/diagnostic-cold"
    mkdir -p "$diag_run"
    sudo -n python3 scripts/latency-run.py env TRASHCAN_REQUEST_PROFILE="$diag_run" \
      target/server-diagnostic/release/trashcan serve \
      "$HOME/models/gemma-4-12b-qat-gguf/gemma-4-12b-it-qat-q4_0.gguf" \
      --batch 128 --port 18160 --no-prefix-cache

The server runs in the foreground. In a separate shell, after it reports readiness:

    python3 results/engine/main-tuning-20261003/server-diagnostic.py \
      --url http://127.0.0.1:18160 \
      --output results/engine/main-tuning-20261003/diagnostic-cold/client.json

This sends warmup(1 output), stochastic(32, seed 7, top_k 32), stochastic repeat, greedy(32),
and greedy repeat. Repeats use SSE by default; --json-only makes all five requests JSON. Every
sent body, terminal response, response ID, elapsed time, and timestamped SSE event is retained.
It checks all four measured requests have 47 input/32 output/0 reasoning tokens and equal text.
Use a fresh server/output directory before replaying the original complete sequence if needed:

    python3 results/engine/main-tuning-20261003/server-diagnostic.py \
      --url http://127.0.0.1:18160 \
      --replay-report results/engine/main-tuning-20261003/prefix-cold.json \
      --output results/engine/main-tuning-20261003/diagnostic-cold-full/client.json

--replay-report sends every exact saved body, including all 19 requests in a complete report.
The explicit input histories in saved tool requests are self-contained, so no response-ID storage
is required. Output differences are retained and reported after the full replay.
For a cached comparison omit --no-prefix-cache and use another fresh directory/process.

The environment gate is checked per generated request. When enabled the patch saves:
- request-NNNN.json: request index, response ID, epoch start, prompt/cache/output counts, sampling,
  prefill duration, and every ordinary forward's input/next token IDs, position, total wall time,
  existing submit/wait/read timings, separate per-GPU segment and gap totals, and head segment times.
- request-NNNN.tsv: generation::profile output for the last actual forward.

Match client and server records by response_id. Each request index starts at 1 in a fresh process.
Compare input_token and next_token sequences, then wall_ms versus submit_wait_read_ms and gpu_ms /
gap_ms. Wall time includes embedding, host writes, and first-use command recording. There are no
extra GPU queries. Large wall-minus-engine-timing suggests host/recording cost; larger gpu_ms or
gap_ms directs inspection to kernels or synchronization. Per-GPU timelines run concurrently and
must not be added to estimate request elapsed time.

File writes happen after the terminal response. request_wall_ms excludes diagnostic file writes;
small diagnostic CPU/file overhead can affect the next request's queueing. A fully cached request
with no forward retains the prior profile, explicitly marked last_profile_from_this_request=false.
Only ordinary target forwards are logged individually; MTP steps are not individually instrumented.
Use separate production measurements for final performance claims.
