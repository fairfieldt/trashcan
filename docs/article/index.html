How we deploy 180B-parameter frontier models on Mac Pros

The trashcan project · October 2026 · after Cerebras’s How we deploy trillion-parameter frontier models on Cerebras

One of the most frequently asked questions we get is how we deploy large models on six 13-year-old Mac Pros connected over Thunderbolt. A single 2013 Mac Pro has 12 GB of GPU memory, as 6 GB of GDDR5 on each of its two AMD FirePro D700s, and 180B-parameter frontier models need over a hundred gigabytes for their weights alone.1

In this post, we walk through how a frontier model is split across multiple Mac Pros so it runs at 20+ tokens per second.

We’ll use Qwen3.8-Flash-Next, a 177B-parameter open-weights model, as the example.

You’ll learn:

  • how the model fits in GPU memory
  • how the model maps across Mac Pros
  • how many concurrent requests it can serve

Breaking it down with Qwen3.8-Flash-Next

Qwen3.8-Flash-Next is a 177B-parameter open-weights model with 36 Gated DeltaNet layers and 12 sparse-attention layers.2

Its quality holds up well against the 8-bit release. With experts quantized to about 4 bits, it picks the same next token 95.1% of the time, with a mean KL divergence of 0.039 over 39K tokens, ahead of every other 4-bit, 3-bit and 2-bit expert format we tried.3

For this example, we’ll assume:

  • 32K average request size
  • about 4-bit experts, 8-bit dense weights
  • 16-bit KV cache

#1: Size of each layer

Before we can figure out how many Mac Pros we need, we need to know how much memory each layer takes.

The weights come to 116 GiB. 51 GiB of that is an n-gram table read once per token, which stays on the first Mac’s SSD, leaving the payload for the GPUs:

116 GiB − 51 GiB n-gram table = 65 GiB

Dividing across 48 layers gives about 1.4 GiB per layer.

65 GiB ÷ 48 layers ≈ 1.4 GiB per layer

#2: Number of Mac Pros

How many layers fit on one 6 GB GPU depends on the layer type:

  • Sparse-attention layers need room for a KV cache that grows with the request, so each GPU holds one, with the rest of its memory left for the cache.
  • DeltaNet layers keep a small fixed-size state per request, so three fit alongside it.

Applying this to 36 DeltaNet and 12 sparse-attention layers gives the GPU count, at two GPUs per Mac:

36 DeltaNet ÷ 3 = 12 GPUs, with 12 sparse-attention ÷ 1 on the same 12
12 GPUs ÷ 2 per Mac = 6 Mac Pros

So we need 6 Mac Pros.4

#3: Connecting the Mac Pros together

The engine assigns each GPU four consecutive layers, and only activations travel between Macs: 40 KiB per token, over Thunderbolt 2 at about 25 µs per round trip.5

Because each 1.4 GiB layer fits easily on a 6 GB GPU, the weights don’t move and no layer is split. Only activations cross between Macs.

#4: How we serve 1 request

Think of the Macs as an assembly line. Each GPU is a station whose layers stay put, and the request’s intermediate results move from station to station.

The first GPU runs layers 0–3 and passes its activations to the second GPU, which runs layers 4–7, and so on around the ring until the last GPU finishes layer 47 and every Mac scores its slice of the vocabulary for the next token.

incite GPU 0
0–3→incite GPU 1
4–7→inflight GPU 0
8–11→…→enlight GPU 1
44–47→next token

#5: How we serve many requests

One might assume the GPUs sit idle while they wait for their turn, so the pipeline effectively runs at batch size one.

That’s correct. Our server runs one request at a time, so while one GPU works on a token, the other eleven wait.6

Within one request, the prompt does keep several stations busy: each GPU works on a different chunk of it, which is how a 30,000-token prompt is read at 1,249 tokens per second against 22.5 tokens per second for generation.7

Micro-batches would let each station take a small group of requests at once. We haven’t built them.

#6: How many requests can we serve?

The GPU memory left over for KV cache sets the maximum number of concurrent requests.

On the busiest GPU, the space left after its layers, its share of the output head and one request’s cache is:

5,869 MiB budget − 5,830 MiB allocated = 39 MiB

Calculating the # of concurrent requests

One 32K request needs this much KV cache for that GPU’s sparse-attention layer:

32,768 positions × 2,048 bytes = 64 MiB

Dividing the space left by the cache per request gives the number of additional requests:

39 MiB ÷ 64 MiB = 0.6 → 1 concurrent request

Concurrent requests here don’t wait on each other like a GPU batch; there is only one.

Concurrency and batch size don’t fully capture efficiency anyway. A better measure is tokens per second per unit of power at a given speed: about 15,150 tokens per second per megawatt, from 20.61 tokens per second at 1,360 W.8

How this scales beyond 180B parameters

Larger models work the same way: calculate the memory for weights and request state, distribute the layers across more Mac Pros, and chain them into a pipeline.
