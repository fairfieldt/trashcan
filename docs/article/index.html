How we deploy 180B-parameter frontier models on six Mac Pros

The trashcan project · October 2026 · a parody of Cerebras’s How we deploy trillion-parameter frontier models on Cerebras

One of the most frequently asked questions we get is how we deploy large models on six nearly 13-year-old Mac Pros connected over Thunderbolt. A single 2013 Mac Pro has 12 GB of GPU memory: 6 GB of GDDR5 on each of its two AMD FirePro D700s, which do not share it. A 180B-parameter frontier model needs over a hundred gigabytes for its weights alone.1

So the model has to be split across machines. This post walks through how we do it and how fast it goes. Every number below is from our own measurements unless it is marked as a calculation or a model.

The question is asked mostly by us.

Breaking it down with Qwen3.8-Flash-Next

Our example is Qwen3.8-Flash-Next, a 177-billion-parameter sparse mixture-of-experts model, which we round to 180B for headline purposes.2 It has 48 layers: 36 Gated DeltaNet layers, which keep a fixed-size recurrent state, and 12 sparse-attention layers, one in every four. Each layer has 512 experts, of which a token uses 10, so only about 6B parameters are active per token. Another 51B parameters are a hashed n-gram embedding table that the model reads at exactly one layer.

We assume a 32K-token context and our six-Mac quantization recipe: experts at about 4 bits, dense matrices at 8 bits, the output head at 6.

“Frontier” is doing some work in the headline. We have run one benchmark, and it measures agreement with itself: against the 8-bit release, our 4-bit recipe picks the same next token 95.1% of the time, with a mean KL divergence of 0.039 over 39K tokens.3

#1How big is each layer?

Start with the file on disk, then remove the part that never needs a GPU. The n-gram table is read once per token, 16 rows of 160 values, so it stays on the first Mac’s SSD and is read through the page cache in 0.4 ms. Nothing else gets to stay on an SSD.

116 GiB weights, six-Mac recipe
− 51 GiB n-gram table, left on the SSD
= 65 GiB that must live in GPU memory
65 GiB ÷ 48 layers ≈ 1.4 GiB per layer // calculated average

#2How many Macs?

12 D700 × 6 GiB = 72 GiB of GPU memory
65 GiB ÷ 72 GiB = 90%, before caches, scratch and the output head
48 layers ÷ 12 GPUs = 4 layers per GPU

Four layers per GPU is three DeltaNet layers and one sparse-attention layer, which is the model’s own repeating pattern. We would like to say this was planned.

Fewer Macs don’t work. Five don’t fit at 4 bits. Four fit only with 2-bit experts, which cost as much quality as quantizing every dense matrix to 4 bits.6 Six it is, which is also how many we have.

That leaves 39 MiB. If a stage goes over, the driver quietly moves the excess into system memory. The one time we allowed that, the output head ran 18 times slower, so now the engine refuses to start.

#3Connecting the Macs together

The six Macs form a ring of Thunderbolt 2 cables. Each GPU keeps its layers resident, so weights never move. Between stages we send only the residual stream: four streams of 2,560 values.

4 × 2,560 × 4 bytes = 40 KiB per token per hop
40 KiB × 8 ÷ 9.6 Gb/s ≈ 34 µs on the wire // calculated
small-message round trip = 25 µs // measured

The 25 µs round trip uses USB4STREAM, a raw Thunderbolt stream device in Linux, which we had to patch for these controllers and give our own retransmission. Thunderbolt networking took 40 µs.7 Before any of this, we had to patch the kernel so the GPUs would leave their battery power state. A Mac Pro has no battery.8

#4How we serve one request

The first Mac embeds the token and reads its n-gram rows. Its first GPU runs layers 0–3 and its second GPU runs 4–7, and the result goes down the cable to the next Mac. After layer 47, the final hidden state travels back around the ring, every Mac scores its share of the 248,320-token vocabulary at the same time, and the best candidates are merged.

Generation runs at 22.5 tokens per second after a 512-token prompt. With speculative decoding, using the model’s own draft layer, chat replies reach 31.3 tokens per second with output identical to plain decoding.12 On the first day it ran at 8.1.

During generation, one GPU works at a time while the other eleven wait for it. Reading every active weight once at the D700’s rated 263 GB/s would allow 47 tokens per second. At the 205 GB/s a D700 actually sustains, plus the time the CPUs spend passing data along, the realistic limit is about 31.

Reading a prompt is more parallel, because each GPU can work on a different chunk of it. A 30,000-token prompt is read at 1,249 tokens per second, in about 24 seconds.

#5How we serve many requests

A common misconception about pipelines is that they serve one request at a time. Ours does.

Micro-batching would let the waiting GPUs work on other people’s requests. We have not built it. There are not, at present, other people.

#6Tokens per second per megawatt

Cerebras points out that the meaningful efficiency metric is tokens per second per megawatt. We agree, and we have measured it.

20.61 tok/s ÷ 1,360 W = 15,150 tok/s per megawatt // calculated

We came to the megawatt part through experience. On October 9, four Macs drawing about 1.65 kW from one power strip tripped it. On October 14, after the Macs had been moved onto separate circuits, all six lost power about 30 seconds after reaching 1.5 kW, along with the workstation recording the measurement. The cause has not been confirmed.15

How this scales

Mostly downward. Four Macs could work if each kept its experts in system memory and cached the popular ones on the GPUs; we estimate 10.8 tokens per second and have not built it. Upward, splitting every layer across all twelve GPUs at once would read each token’s weights in about 2 ms, but it would need about 96 exchanges across the ring per token at 100 µs or more each. We estimate 50–80 tokens per second, at a large cost in engineering.16

The method itself is the same at any size: work out how much memory the weights and the request state need, divide the layers across the hardware, and connect the pieces into a pipeline. In our case, the remaining step is to keep the fan at 2,350 RPM.
